# SDCC PROM1-only polypascal-test fix — stale xport_aliases.asm

Date: 2026-05-18
Status: **FIXED** at commit on main 2026-05-18 morning.

## Result

| Compiler | Result | Time |
| -------- | ------ | ---- |
| clang    | PASS   | 51.33 s |
| SDCC     | PASS   | 49.67 s |

Test: `COMPILER={clang,sdcc} TRANSPORT=pio-irq make cpnos-polypascal-test`

Both compilers now drive the PROM1-only line program through a full
PolyPascal-80 PRIMES workload via CP/NET (PRIMES through 29989, Q
returns to E>).

## Root cause

The Makefile generates `$(BUILDDIR)/xport_aliases.asm` (a 3-byte JP
trampoline file that lets SDCC's `_xport_send_byte` / `_xport_recv_byte`
resolve to the chosen TRANSPORT impl).  The original rule:

```
$(BUILDDIR)/xport_aliases.asm: $(BUILDDIR)/transport_stamp
```

`transport_stamp` is updated via `$(shell)` at parse time when the
current `TRANSPORT` value differs from the file's content -- standard
mtime-driven invalidation.

The trap: if `xport_aliases.asm` ends up newer than `transport_stamp`
through any path (e.g. an interrupted build that regenerated only the
asm, or a `make sdcc/xport_aliases.asm` target run with a mismatched
TRANSPORT env that the parse-time check didn't propagate to), make
considers it up-to-date and skips regen.

Observed today: `sdcc/transport_stamp` content was `pio-irq` but
`sdcc/xport_aliases.asm` header said `; Generated by Makefile from
TRANSPORT=sio.` -- so the asm pointed `_xport_send_byte` at
`_transport_send_byte` (SIO impl).  The SDCC PROM1-only slave ran
with TRANSPORT=pio-irq, MAME wired PIO-B to cpnet_bridge :4002, and
the slave silently dispatched CP/NET frames to **SIO-A** (a raw file
sink, `/tmp/cpnos_sioa.raw`) -- no master, no response, slave hung
in the LOGIN ACK wait.

Wire-tap on :4003 (proxy in front of mpm-net2) confirmed the slave
sent ONLY one byte (0x00, the PIO mode-switch stale m_output) before
going silent.  Clang's identical source worked by accident: its
`make prom1-lineprog` invocation took the same TRANSPORT path but
its build state happened to regenerate `clang-prom1lineprog/...` via
a different code path that didn't share the SDCC asm-stamp issue.

## Fix

Replace the dep-chain rule with a content-driven `$(shell)` regen,
matching the pattern already used for `transport_stamp`:

```make
ifeq ($(filter clean cpnos-clean,$(MAKECMDGOALS)),)
_DUMMY_XPORT_ALIASES := $(shell mkdir -p $(BUILDDIR); \
    if ! grep -q "from TRANSPORT=$(TRANSPORT)\." $(BUILDDIR)/xport_aliases.asm 2>/dev/null; then \
        { ... echo lines that emit asm with current TRANSPORT ... } > $(BUILDDIR)/xport_aliases.asm; \
    fi)
endif
```

At parse time, the .asm header is grep'd for `from TRANSPORT=$(TRANSPORT).`;
if absent, the file is rewritten with the current TRANSPORT.  Survives
any combination of dep-chain weirdness because the check is on the
file's *content*, not its mtime.

Verified: artificial regression (sed-rewriting the header to `sio`)
triggers parse-time regen on the next `make`, restoring the correct
content.

## Diagnostic timeline (this session)

- BOOT_MARK trail showed slave reached NTWKIN ok (`I.........PNI`)
  but never `LOGIN ok`.  Localised the stall to `cpnet_xact(64, 7)`.
- Manual netcat probe of mpm-net2 on `:4002` confirmed master is
  responsive (ENQ→ACK in <50ms).
- TCP MITM tap (`python /tmp/cpnet_tap.py` between MAME's `-bitb3
  socket:4003` and mpm-net2's `:4002`) captured what was actually on
  the wire: SDCC sent `00` then silence; clang sent `00 05` then full
  LOGIN frame.
- The `00` is the PIO mode-switch stale `m_output` (well-documented in
  `transport_pio.c` lines 130-145).  Master tolerates this prefix.
- One failed fix attempt: rewriting `transport_pio_send_byte` to
  always emit data via the FAST path after mode switch.  Broke clang
  (introduced byte duplication on every direction flip — MAME's PIO
  set_mode(INPUT) re-emits m_output on the wire).  Reverted.
- Reading the *clang* PROM1 wire vs the *SDCC* PROM1 wire highlighted
  that SDCC's slave never even sent its own ENQ.  That pointed at the
  call-routing layer (xport_aliases.asm) rather than the PIO byte-level
  code.
- The `head -1 sdcc/xport_aliases.asm` revealed the SIO target.  Root
  cause located.

## Lessons / generalisations

1. **`make`'s mtime-driven dep invalidation is fragile for stamped
   build artifacts.**  When a generated file's content depends on a
   build-variable (TRANSPORT, COMPILER), use parse-time content checks
   (`$(shell)` + `grep` of an embedded marker) rather than relying on
   the variable's stamp file alone.
2. **Wire-level traces should be the first move when "CP/NET hangs".**
   30 seconds of `python -c` netcat MITM was decisive.  Without it I
   would have kept chasing PIO timing red herrings.
3. **Compare wire byte streams across compilers when same-source-
   different-output.**  Clang's `00 05` vs SDCC's `00` was the smoking
   gun that the bug wasn't in the SOURCE but in the LINKING.

## Memory rules invoked / proposed

This bug pattern matches but isn't quite covered by:
- `feedback_check_banner_timestamp.md` (banner pre-flight) — catches
  ROM-side staleness, not Makefile-side artifact mismatch.
- `feedback_symmetric_recipes_per_compiler.md` (parallel COMPILER
  recipes must emit same artifact set) — adjacent but different
  class (this was a TRANSPORT-keyed artifact going stale, not a
  COMPILER-keyed asymmetry).

**Proposed new rule:** "**Build-variable-dependent artifacts must
content-check, not mtime-check.**  When a generated file's content
depends on a build-time variable (TRANSPORT, COMPILER, WORKLOAD,
etc.), the regeneration trigger must be `$(shell)` parse-time grep
of an embedded marker, not a stamp-file mtime dep.  mtime can go
stale through interrupted builds, parallel sub-makes that don't
inherit the variable, or generated-output rules invoked with
override args."
