# Plan: tackle ravn/z88dk#8 (switch dead-code) and #10 (IX-frame)

Date: 2026-05-19.
Status: investigative; no code yet.

These are the two SDCC-z80 backend gaps surfaced in
`cpnos-in-c/tasks/sdcc-codegen-gap-2026-05-18.md` and filed upstream
in our ravn fork of z88dk.  Both originate inside z88dk's bundled
SDCC tree at `z88dk/src/sdcc-build/src/{z80,SDCC*}`.

## #8 — switch with tail-callable cases emits dead `jp` block

### Mechanism (confirmed in source)

1. `SDCCicode.c:geniCodeSwitch` lowers `switch (x) { case N: f(); break; }`
   to a compare-chain plus a body chain:

   ```
   cmp x,N1 ; if-true goto _case_N_1
   cmp x,N2 ; if-true goto _case_N_2
   ...
   goto _swBrk_N
   _case_N_1: call f1; goto _swBrk_N
   _case_N_2: call f2; goto _swBrk_N
   ...
   _swBrk_N: <return>
   ```

   The case **bodies** are emitted unconditionally even when the
   dispatch later collapses past them.

2. At asm level, two z80 peepholes do the collapse:

   * `peeph.def:1202` (pho 84): `jp cc, %5` where `%5: jp %6` rewrites
     `jp cc, %5` -> `jp cc, %6`, dropping `%5`'s refcount.

   * `peeph.def:3030` (pho 159): `%1:` with `labelRefCount(%1 0)`
     removes the label.

3. After both fire, the case-body block looks like:

   ```
   ret              ; default fallthrough exit
   jp _a            ; ex-_case_N_1, label removed by pho 159
   jp _b
   jp _c
   jp _d
   ```

   These are unreachable but the asm peephole has no rule to delete
   `jp` instructions following an unconditional terminator (`ret` /
   `jp`).  `--fomit-frame-pointer` + tail-call eligibility are
   required for the rewrites to fire, which is why `-Cs"--sdcccall 1
   --fomit-frame-pointer"` reproduces and the default frame-pointer
   path doesn't.

### Fix approaches (ranked)

**A. New asm peephole "drop instructions after unconditional flow exit".**
Add to `peeph.def` immediately before barrier 3038 (where label-159
sits):

```
replace restart {
    ret
    jp  %1
} by {
    ret
    ; common peephole NNN removed unreachable jp after ret.
} if labelRefCountChange(%1 -1)

replace restart {
    jp  %2
    jp  %1
} by {
    jp  %2
    ; common peephole NNN+1 removed unreachable jp after unconditional jp.
} if labelRefCountChange(%1 -1)
```

Iterates via `restart`, so a chain of 4 orphan `jp`s collapses one at
a time.  `labelRefCountChange(%1 -1)` keeps `_a`'s refcount honest if
`_a` happens to be a local label (it's usually an extern func symbol;
the change is a no-op on extern symbols which is correct).

Risk:
- false positive if `%1` is a local label that's the actual entry
  for trailing code reachable via fall-through from somewhere else.
  But after `ret`/`jp`, the only way to reach the next byte is via
  a label, and we don't touch instructions that follow a label
  (the pattern doesn't include `%2:` between).

This is the cheapest, most-targeted fix and stays at peephole level
(no CFG analysis needed).

**B. Move the rewrite into `SDCClabel.c`.**
After `labelGotoGoto` and `labelUnrefLabel` run, walk the iCode
chain and remove `iCode`s after `GOTO`/`RETURN` until the next
`LABEL`.  More principled (does dead-block deletion on the IR), but
in this case the rewrite that creates the orphan happens at the asm
peephole layer -- not at iCode -- so an iCode-level pass would miss
the trigger.  Reject.

**C. Suppress emission of the case body block at `geniCodeSwitch` time
when the case body is a single tail-callable statement.**
SDCC would need lookahead during switch lowering: if every case body
is "call f; break", emit only the dispatch `jp cc, _f` directly and
skip body emission.  Big refactor, affects all backends, way more
risk.  Reject.

### Plan for #8

1. Implement approach **A** in `peeph.def`.  Add the two `replace
   restart` rules above the barrier at 3038.
2. Verify the `f(x)` repro shrinks 33 B -> 21 B.
3. Run SDCC's own regression suite from the z88dk tree to ensure no
   new failures.
4. Build `cpnos-in-c COMPILER=sdcc` and `rcbios COMPILER=sdcc`,
   measure size delta, run cpnos-polypascal-test + rcbios polypascal-pio
   regressions.
5. Open a PR against `ravn/z88dk` (the user's fork; never upstream
   per memory rules) with peephole, golden test from the repro, and
   the size numbers.

Estimated size win on real code: cpnos jumptable callsites (~30 case
emit_seq dispatchers) collapse ~120-200 B.  Worth measuring.

## #10 — IX-frame when spills survive a call

### Mechanism (confirmed in source)

`z80/gen.c:7020` ("emitFunctionPrologue"):

```c
if (!IS_SM83 && !z80_opts.noOmitFramePtr && !stackParm && !sym->stack)
    _G.omitFramePtr = true;
else if (sym->stack)
    /* emit full IX frame */
```

`sym->stack > 0` whenever the function has any auto local OR any
ralloc spill that ended up on the stack.  `z80/ralloc.c:288`
explicitly says:

```c
// z80 port currently only supports on-stack spill locations in code
// generation.
```

So if ralloc needs to spill `row.lo`/`row.hi` across a call (the
canonical case in the issue), it calls `createStackSpil`, which sets
`sym->stack`, which forces `_G.omitFramePtr = false` -> ~13 B
prologue + 4 B epilogue + 3 B per access instead of `ld (sloc), a` /
`ld a, (sloc)` (3 B per access, zero prologue).

### Fix approaches (ranked)

**D. Lift the "z80 only supports on-stack spill" restriction in gen.c
load/store paths.**
The blocker is gen.c's aopOp/aopGet/storeRegToAop/etc.  When a sym's
spill location is in `data` (BSS), they need to emit `ld (sloc), a`
instead of `ld (ix-N), a`.  This is the textbook fix and is what
hc08/stm8/pic16 ports do.

Concrete sub-tasks:
- Audit every `aopGet`/`aopPut` path in gen.c that special-cases
  `AOP_STK` / `AOP_EXSTK`.  Each needs an `AOP_DIR` (data
  directly-addressable) alternative for spill sites.
- Replicate `createStackSpil` as `createDataSpil` (or extend) that
  picks between stack and data based on heuristics:
    * function is `!isReentrant` AND `!IFFUNC_ISISR` AND not recursive
    * total spill size bounded (don't fill BSS)
    * RC702-specific: stay out of the IVT page / display memory
      (caller responsibility; SDCC just allocates static globals
      which get linked normally)
- Drop the wassert at line 288 in ralloc.c.

Size: estimated 15-25 B per IX-frame function eliminated.  In rcbios
the candidates are `_specc` (676 B), `_bios_hw_init` (341 B),
`_isr_crt` (166 B), etc. -- many.  Total potential: ~150-250 B on
rcbios.

Risk: high.  This is a multi-day gen.c refactor touching the most
delicate AOP plumbing.  Easy to introduce miscompiles.

**E. Cherry-pick from upstream SDCC.**
Check whether upstream SDCC (after the snapshot z88dk has bundled)
has already added data-spill support to z80.  z88dk bundled SDCC is
`src/sdcc-build/src/` -- a snapshot of mainline SDCC at some date.
If upstream has the fix, we cherry-pick rather than re-implement.

Sub-tasks:
- Find z88dk's bundled SDCC version (`grep -n SDCC_VERSION` in
  src/sdcc-build/src/SDCCutil.c or `src/.version` or similar).
- Diff against current mainline SDCC z80 ralloc.c + gen.c looking for
  data-spill changes.
- If found, port the patch onto our z88dk tree.

This is the right thing to try **first** before re-implementing.

**F. Implement at C-source level using `static` locals.**
Sidestep the compiler bug by writing `static unsigned char row_lo,
row_hi;` in user code where spill-across-call is unavoidable.
Rejected by `feedback_dont_fight_sdcc_icode` memory rule: forces
static for variables SDCC would otherwise keep in registers in the
common case (single-BB live range), pessimizing the unaffected hot
paths.  Reject for general use.

### Re-spill semantics analysis (2026-05-20 followup)

Looking more closely at z80SpillThis's gate at ralloc.c:288:

```c
if (!(sym->remat || sym->usl.spillLoc) ||
    (sym->usl.spillLoc && !sym->usl.spillLoc->onStack))
    createStackSpil (sym);
else
    /* reuse existing spillLoc */
```

The gate conflates two distinct triggers:

  a. **First-time spill** (`!sym->usl.spillLoc`): create one.
  b. **Re-spill discard** (`sym->usl.spillLoc && !onStack`):
     destroy an off-stack spillLoc and replace with an on-stack
     one.

For #10, (a) keeps; (b) must be dropped (it would actively
undo the data-spill on each re-spill).  The PoC dropped (b),
correctly.  The crash was downstream in gen.c, not from this
gate.

The else branch (line 290) is *load-bearing* once #10 lands:
subsequent z80SpillThis calls for a symbol with a data spillLoc
need to **reuse it**, not recreate.  This is fine -- the else
branch already does the right thing; just needs the gate-(b)
lifted to reach it.

## Appendix: switch-vs-if-else size heuristics in both compilers

(Investigation 2026-05-19, after #8 landed and `specc()` was rewritten.)

Both clang and SDCC already have size-aware switch lowering, with
**different shapes**:

### clang / LLVM

`TargetLoweringBase::isSuitableForJumpTable` (TargetLoweringBase.cpp:2060)
gates JT on **density** plus **minimum entries**.  Two density
floors:

  * Default: 10 % (`-jump-table-density=10`)
  * **-Os / -Oz: 40 %** (`-optsize-jump-table-density=40`, picked
    via `getMinimumJumpTableDensity(OptForSize)`)

Plus `getMinimumJumpTableEntries` (default 4).  The Z80 backend
**overrides this to 8** in `Z80ISelLowering.cpp:62` with the
comment:

> "Z80 jump-table dispatch costs ~19 bytes (zero-extend, table
> lookup, indirect jump) + 2 bytes per entry.  Cascaded CP/JR Z
> branches cost ~4 bytes per case.  Jump tables only win for
> ≥ 8 cases.  The LLVM default is 4, which generates jump tables
> for 4-case IOBYTE dispatches that are 15+ bytes larger than the
> equivalent if-else chain."

That's a universal floor (not gated on -Os), but the density floor
DOES tighten with -Os.  GlobalISel (which Z80 uses) goes through
`SwitchCG::findJumpTables` → `isSuitableForJumpTable`, so it
respects both.

### SDCC

`geniCodeJumpTable` (SDCCicode.c:4017) is **always size-driven**,
no opt-level toggle.  It compares:

```
sizeofJumpTable = (max-min+1) * sizeofElement + sizeofDispatch + range-check cost
sizeofMatchJump = numCases * sizeofMatchJump[sizeIndex]
```

picks the smaller.  Z80 cost table (z80/main.c:1177):
`sizeofElement=3`, `sizeofMatchJump={6,7,8}`, `sizeofDispatch=9`,
`sizeofRangeCompare={6,9,15}`.

### Applied to `specc()` (14 cases, range 0x01..0x1F = 31)

  * **SDCC**: JT 31×3 + 9 + 12 = 114 B vs match-jump 14×6 = 84 B
    → chose match-jump.  *Correct call.*
  * **clang -Os**: density 14/31 ≈ 45 % ≥ 40 % Os floor, ≥ 8
    entries → chose JT.  *Per-byte close call.*

Both around 85 B by different paths.  Neither sorts cases by
frequency (no PGO data), so for hot-byte latency the order matters
more than the algorithm.

### Why my manual if/else still shrank SDCC by 20 B

SDCC's heuristic chose match-jump (84 B estimate), but the
**emitted** match-jump was ~95 B in reality.  Reason:

  1. iCode switch lowering emits `cp X; jp Z, _case_N_X` dispatches
     plus separate `_case_N_X: call _handler; goto _swBrk` body
     blocks.
  2. Peep 84 (`jp cc, %5` where `%5: jp X` → `jp cc, X`) tail-call-
     fuses each case dispatch into a direct `jp cc, _handler`.
     Works.
  3. Peep 154 (`jp cc, %5` → `jr cc, %5` when in range) runs in
     parallel, converting un-fused dispatches to JR.
  4. Peep 84 **only matches `jp`, not `jr`**.  Once a dispatch
     becomes `jr cc, _case_N_X`, peep 84 can no longer rewrite it
     to the handler.

So the first ~4 cases (where peep 84 fires before peep 154 wins
the race) get the ideal 5 B/case form.  The remaining ~10 stay
routed through their `_case_N_X:` body labels at ~9 B each.

The manual if/else bypasses the iCode-level switch machinery: each
`else if (c == X) handler();` is its own atomic ifx + tail-call
that hits the 5 B form independently of peep ordering.

**Possible upstream fix for SDCC**: teach peep 84 to also match
`jr cc, %5`, with appropriate range check.  Would tighten any
many-case switch with tail-callable bodies, not just specc.
Filed as orphan note in this doc; not yet a ravn/z88dk issue.
